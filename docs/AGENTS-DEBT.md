## Known Issues / Architectural Debt

### Two Combat State Components (SYNCED — issue C / #136 unifies them)
Two ECS components track combat state: `CombatStateComponent` (authoritative — synced from FSM by CombatSystem, used by HUD/StaminaSystem/DamageSystem) and `CombatStateComp` (animation mirror — has `phaseElapsed`/`phaseTotal`/`phaseT`, used by AnimationSystem). **Both are synced by CombatSystem** after FSM tick (fixed in PR #36). Phase math (`getPhaseTotal()` / `getPhaseT()`) lives on `CombatFSM` — `CombatSystem` mirrors those values onto `CombatStateComp` each tick. **Issue C / #136 collapses these into a single `CombatState` component** — see `docs/combat-fsm-v2.md` §9.

### Direct State Writes Bypass the FSM (PARTIALLY RESOLVED by #135 — issue E finishes it)
`StaminaSystem`'s direct `CombatStateComponent.state = Stunned` write was fixed by #135 — it now dispatches `CombatInput.BlockBreak` to the FSM. `DamageSystem` still has direct writes for two branches (`WasParried → HitStun` on attacker, `BlockedHit → Recovery` on attacker) — these are issue E's territory. The funneled-writes invariant (only `_transitionTo()` writes `_state`) is enforced by a static-analysis test on `CombatFSM.ts`, but consumers can still bypass by writing to the ECS component directly; issue E closes the last two bypasses. **Canary test (#174 / `src/ecs/systems/CombatStateBypass.test.ts`)** scans every `src/**/*.ts` file via `import.meta.glob('?raw')` for direct `CombatStateComponent.state[X] = Y` writes; tolerates an explicit allowlist (init in `createPlayer`/`createTrainingDummy`, FSM-ECS sync in `CombatSystem`/`StaminaSystem`/`createTrainingDummy`, death reset in `processDeaths`, no-FSM fallback in `StaminaSystem`) and a `KNOWN_141_BYPASSES` map listing the three `DamageSystem.ts` lines #141 will fix. Any NEW direct write outside the allowlist fails CI loudly. When #141 lands, delete `KNOWN_141_BYPASSES` and the canary tightens automatically.

### Dev-Mode FSM Instrumentation (#174 — PR #179)
Two dev-only tools live in `src/combat/CombatFSM.ts`, both gated by `import.meta.env.DEV` AND a runtime `FSM_TRACE_ENABLED` flag (default `import.meta.env.DEV`) so Vite tree-shakes the entire log/warn block from production builds — the build was verified to contain zero `[FSM]` / `phaseTotal=0 in` / `FSM_TRACE_ENABLED` references after `npm run build`. (1) **Transition logging** — `_transitionTo` emits `[FSM] <eid> <Old> → <New> (input: X, dir: Y, tick: Z)` on every state change; auto-transitions fired by `_onPhaseEnd` log as `input: auto`. The `_lastInput` tracker on `transition()` is wrapped in `try/finally` so it clears even if a handler throws. (2) **`phaseTotal=0` watchdog** — `_assertPhaseTotal()` is called from `_enterWindup`/`_enterRelease`/`_enterRecovery` after the weapon-config lookup; if `_phaseTotal === 0` (a misconfigured weapon would otherwise freeze the FSM at `phaseElapsed = phaseTotal = 0`), it `console.warn`s the weapon name + direction in dev and **unconditionally falls back to `_phaseTotal = 1`** so production never freezes. The fallback runs in BOTH dev AND prod; only the warn is dev-gated. **Tests for the silent-prod contract**: `CombatFSM.test.ts`'s `'source: every [FSM] reference sits inside an import.meta.env.DEV guard'` does brace-counted static analysis on the source file. **Wiring change**: `CombatFSM` constructor now takes `(weaponConfig, eid = 0)`; `createFSM(eid, weaponConfig)` threads the eid through. Tests that construct `new CombatFSM(weapon)` directly default to eid 0. Direct callers can opt out of trace via `setFsmTraceEnabled(false)` (test-only API).

### First-Person Viewmodel (IMPLEMENTED — PR #57, skeletal PR #68, animation PR #70, anchor fix #81, grip data + cache #125, layer-leak guard #173, viewmodel sync #132)
`ViewmodelRenderer` (`src/rendering/ViewmodelRenderer.ts`) renders a procedural right arm + weapon in FPS mode using Two-pass Layer architecture: Layer 0 = world, Layer 1 = viewmodel. Separate `PerspectiveCamera` (FOV 70, near 0.01). Weapon swaps automatically via `onEquip` listener. `CameraController.setViewmodel()` toggles visibility on F5 camera mode switch. **Bone-driven skeletal arm** (PR #68): arm is built from a `THREE.Bone` hierarchy (`vm_upper_arm_R → vm_forearm_R → vm_hand_R → vm_weapon_attach`) with `THREE.SkinnedMesh` parts. `bones` record exposed with canonical names (without `vm_` prefix) for animation system use — keys match AnimationData.ts bone names. **Per-weapon grip data** (#125): `vm_weapon_attach` is no longer pre-rotated at construction. Each `WeaponModelResult` (in `src/rendering/CharacterModel.ts`) optionally carries `gripOffset: Vector3` and `gripRotation: Euler` fields; `swapWeapon(name)` copies those onto `vm_weapon_attach.position` / `.rotation`, so each weapon sits in the hand at its own tuned angle (Longsword `(π·0.85, 0, 0)` preserves the legacy value, Mace `(π·0.75, 0, -0.15)`, Dagger `(π·0.90, 0, 0)` + Z offset `-0.02`, Battleaxe `(π·0.80, 0, 0.1)` + Y offset `-0.05`). Weapons that omit grip fields fall back to `(0, 0, 0)` position and the legacy `(π·0.85, 0, 0)` rotation. **Pre-warmed model cache** (#125): the constructor calls each registered factory exactly once and stashes the `WeaponModelResult` in a `weaponModelCache: Map<string, WeaponModelResult>`. After init, `swapWeapon` is a re-parent + grip apply with **zero allocations** — the same cached `THREE.Group` instance is reused across an arbitrary number of A→B→A→B swaps. `dispose()` walks the cache and disposes every cached weapon's geometries + materials. **Single-source-of-truth registry** (#125 cleanup): `weaponFactories` defaults to importing `weaponModelFactories` from `src/rendering/WeaponModels.ts`, so `main.ts` no longer inlines the factory list. The same registry feeds InventorySystem (3rd-person model swap on equip) via a single `Object.entries(weaponModelFactories)` loop. **Layer-leak guard + factory contract** (#173 — PR #176, after parent #171 forensic): two-pass rendering depends on every `Object3D` under the viewmodel group sitting on `Layer 1` — the world camera renders Layer 0 only (after `scene.background` is nulled), so any child that drifts to Layer 0 would render in the world pass and visibly z-fight + render through walls (the symptom #171 was investigating). To close the latent hazard of a future factory that mutates its cached `Group` post-warm-up (adds runtime children, swaps materials, etc.), `swapWeapon` re-applies `setLayerRecursive(cached.group, VIEWMODEL_LAYER)` after re-parenting + grip — one cheap traverse per swap (swaps are rare equip events, not per-frame). The guard's scope is **`cached.group` only** — arm bones and the `setDebugMode` `AxesHelper` set live outside the cached weapon group and are deliberately untouched (the helpers got Layer 1 at their own allocation site). The PR also introduces the **`WeaponModelFactory` type alias** in `WeaponModels.ts` whose JSDoc spells out two invariants every factory in `weaponModelFactories` (and any test fake passed via `ViewmodelRendererOptions.weaponFactories`) must obey: (a) **post-cache immutability** — do not `group.add(...)` from animation/render code after the factory returns; if a weapon needs runtime children (FX, status indicators), build them once inside the factory and toggle `.visible` from the consumer; (b) **fresh materials per call** — shared `MeshStandardMaterial` instances would leak `PickupRenderer.opacity` fade state across active pickups (same invariant #127 already relied on, now centrally documented). The defensive guard is belt-and-braces; the contract is the source of truth. Both `weaponModelFactories` and `ViewmodelRendererOptions.weaponFactories` are typed as `Record<string, WeaponModelFactory>` for consistency. Eight new contract tests pin both the layer invariant (construction-time across all 4 weapons + 100-cycle A→B→C→D→A stress with intra-loop spot-check + real-factory stress + debug-mode AxesHelper isolation + hostile-post-cache-mutation rescue) and cache stability (A→A reference equality + A→B→A reference equality + 100-cycle stress with all factory call counts pinned at 1). **Anchor convention** (#81): the shoulder bone (`vm_upper_arm_R`) is positioned at the group origin `(0, 0, 0)`, so the entire visible arm hangs DOWN into the viewport via negative-Y child offsets (forearm at `-UPPER_ARM_H`, hand at `-FOREARM_H` from forearm, etc.). `ARM_OFFSET = (0.25, -0.10, -0.4)` places the group origin (= shoulder anchor) slightly below the camera, so the arm enters the screen from the lower-right corner. Do NOT raise the shoulder above the group origin — that's the bug fixed in #81 (upper-arm box clipped into the top-third of the viewport). **Viewmodel animation** (PR #70, rewritten by #132): `ViewmodelAnimationSystem` (`src/rendering/ViewmodelAnimationSystem.ts`) drives bone poses based on `CombatStateComp`. As of #132, it shares the **same shared `applyPoseLayer` / `computeArcSwingPose` pipeline as the third-person `AnimationSystem`** — no more independently-buggy copies of the blend math. Per-entity snapshot side-table (`prevPoseSnapshots`), reads `CombatStateComp.phaseT` directly (no more `phaseElapsed/phaseTotal` math), and Release uses the arc-swing target with `smoothstepEase(crossfadeT)` blend. Non-Release states still read per-weapon poses via `getViewmodelPose()` (#183's positive-X convention rewrite). Idle sway from #129 is layered post-slerp via quaternion multiply. Runs in `update(dt)` after `animationSystem()`. **Animation write-permissions** (doc §3): `ViewmodelAnimationSystem` may write `quaternion` (and read/write `position` for breathing) on `upper_arm_R`/`forearm_R`/`hand_R`. It MUST NOT touch `weapon_attach` — that bone's transform is owned by per-weapon grip data, and any animation write would override the grip and visibly swing the weapon relative to the hand.

### Viewmodel Inertia / Locomotion Bob / Multi-Bone Sway (#129 — final ship gate of #90)
Three layered changes turn the viewmodel from a "2D overlay glued to the camera" into something that reads as a 3D arm in the world. All visual-tuning constants live in **`src/rendering/ViewmodelTuning.ts`** (new module — anchor + lag tau + bob magnitudes + idle sway channel table). `ARM_OFFSET` moved here from `ViewmodelRenderer.ts` per doc §2.2.

**Aim-sway lag** (doc §7): `ViewmodelRenderer.syncWithCamera` is now `(camera, dt, velX, velZ)`. Group + viewmodel-camera quaternions slerp toward the world camera with `alpha = 1 - exp(-dt / AIM_SWAY_TAU_SECONDS)` (τ=80 ms). Position is **never** lagged — only rotation. The viewmodel CAMERA's quaternion is lagged in lockstep with the GROUP's so the arm doesn't swim in screen space (snapping the camera but lagging the group is a known gotcha — the camera frame would move under the arm). New `viewmodel.snap(camera)` hard-copies the camera quaternion to bypass the lag for one frame; called on `RespawnEvent` so the player doesn't see a delayed swing right at the moment they need to reorient. `snap()` also resets the bob accumulator. Frame-rate independent — 30 Hz vs 144 Hz converge to the same closed-fraction over equal sim time.

**Locomotion bob** (`src/rendering/ViewmodelBob.ts`, doc §6): module-level `walkAmount` (smoothed scalar in [0,1]) + `stridePhase` (monotonic accumulator). `updateBob(dt, velX, velZ)` returns reused `{dx, dy}` (zero per-frame allocations). Math: `targetWalk = clamp(speed/WALK_SPEED, 0, 1)` (`WALK_SPEED = 4 m/s`), `walkAmount` smooths to target with τ=150 ms (avoids snap-to-zero clip when the player stops mid-stride), `strideFreq = lerp(STRIDE_FREQ_MIN=1.6, STRIDE_FREQ_MAX=2.6, walkAmount)` Hz, `dy = sin(stridePhase·2π·2) · 0.012 · walkAmount` (vertical, 2× stride freq — each footfall = one peak), `dx = sin(stridePhase·2π) · 0.008 · walkAmount` (horizontal, 1× — full sway per stride pair). Bob added to `ARM_OFFSET` in camera-local space BEFORE rotating into world space, using the WORLD camera quaternion (not the lagged one — coupling bob to the lag would feel mushy). `resetBob()` is called on respawn via `snap()`. **Velocity source**: `(Position - PreviousPosition) / FIXED_TIMESTEP` from main.ts. Kinematic-position-based bodies don't populate Rapier `linvel()`, and `Velocity.x/.z` aren't written by any system today — Position deltas are the canonical horizontal velocity until a future refactor adds a proper writer.

**Multi-bone idle sway** (doc §5): replaces the old single-axis hand+forearm sway. Five mutually-prime sinusoids (frequencies 0.27 / 0.31 / 0.35 / 0.40 Hz, LCM far larger than any session) layered post-slerp via quaternion multiply: `upper_arm_R` Y@0.35Hz·0.012rad + X@0.35Hz+π/2·0.006rad (breathing — slow chest rise, paired axes at quarter-cycle phase), `hand_R` X@0.27Hz+1.0·0.008rad + Z@0.31Hz+2.1·0.005rad (hand drift — independent of breath), `forearm_R` Z@0.40Hz·0.004rad. Channel table in `ViewmodelTuning.IDLE_SWAY_CHANNELS`. Amplitudes <0.015 rad (≈ <1°) — viewer reads "alive" rather than "drifting". **Gated to Idle ONLY** — combat poses already animate the arm and stacking sway on top would fight them; HitStun/Block/Recovery/Parry/etc. are explicitly excluded. The post-slerp position avoids the subtle bug of pre-slerp sway getting blended away during state-entry crossfade.

**main.ts wiring**: `lastUpdateDt` cached from `loop.update(dt)` and read in `loop.render(alpha)` (GameLoop's render gets `alpha`, not `dt`; capturing across the boundary is sound because update + render run in lockstep). `viewmodel.syncWithCamera(world.camera, lastUpdateDt, velX, velZ)` in render loop. `EventBus.on('RespawnEvent', ...)` calls `viewmodel.snap(world.camera)` for the player only. `--debug-viewmodel` overlay's `aimSwayDeg` field is no longer a `null` placeholder — it's `viewmodel.group.quaternion.angleTo(world.camera.quaternion) · 180/π`, which hovers near 0° at rest and spikes briefly during fast aim flicks.

### Arena Authoring (Arena v1 LANDED — #112 / PR #164, after #117 lighting / #91 parent)
Arenas are **code-authored** — pure TypeScript, no glTF or JSON map files. `createArena(world: GameWorld): ArenaSpec` builds Three.js meshes + matching Rapier static colliders (`RigidBodyType.Fixed` + `cuboid`) 1:1 with mesh extents. Lights live inside `createArena()` (not `World.ts`) — they're map data, not engine data. The returned `ArenaSpec` is stored on **`GameWorld.arena?: ArenaSpec`** (new optional field on the `GameWorld` interface in `core/types.ts`) for systems (spawn, weapon-pickup, shopkeep AI, dummy spawn) to query without re-importing.

**v1 inventory** — 9 static props built in design-doc order (ground → 4 walls → 2 pillars → counter → back wall) so collider/body indices are predictable for tests:
- **Ground** — 30 × 0.2 × 30 olive cuboid centered at origin; top surface at **`y = 0.1 = GROUND_TOP_Y`** (the feet-origin invariant — both `spawnAtGround`'s fallback and `core/types.ts` math depend on this; do not change without updating the constant).
- **4 perimeter walls** — 2 m tall warm-grey, slight overlap at corners (no seams), at `x = ±15.25` and `z = ±15.25` (centerline).
- **2 cover pillars** — 2 × 3 × 2 light-grey at `(±5, 1.5, 0)`, mirror-symmetric across `z = 0`.
- **Shop counter** — 3 × 1 × 0.5 wood-brown at `(-12, 0.5, 12)`; **shop back wall** — 0.5 × 3 × 4 at `(-13.25, 1.5, 12)`. SW corner.

A small `addStaticBox(center, size, color)` helper inside `createArena` enforces the **mesh-full vs collider-half-extent** translation: Three.js `BoxGeometry(w, h, d)` takes full extents, Rapier `cuboid(hx, hy, hz)` takes half-extents, and the helper does `(size.x/2, size.y/2, size.z/2)` automatically. New props belong inside this helper to keep the 1:1 invariant intact (asserted by `createArena.test.ts`'s `mesh and collider extents are 1:1` test).

**Spawn-point ground truth** — the arena is now the sole producer of `spawnPointRegistry` entries. `createArena` calls `clearSpawnPoints()` first (wipes any test-leftover or prior-call entries), then registers the 6 design-doc spawn points S1..S6. The `arena/types.ts` `SpawnPoint` shape uses `{id: string, position, facing}`; the `world/SpawnPoints.ts` registry uses `{id: number, position, yaw}` — the two schemas coexist by design and `createArena` translates once (string `s1..s6` → numeric `1..6`; `facing → yaw`). **1-based numeric ids** keep `id=0` as the "no spawn point" sentinel for `RespawnEvent.spawnPointId`.

**ArenaSpec fields** — `name: 'arena_v1'`, `groundHeight: 0.1`, `bounds` (inside-walls AABB at `x/z ∈ [-15, 15]`, `y ∈ [0, 10]`), `spawnPoints` (6 entries with string ids), `shopkeepStall` (counter AABB, `npcAnchor: (-12, 0.1, 13)`, `facing: 0` = -Z = north into arena), `weaponPickupSafeVolume` (bounds shrunk by 0.5 m margin so dropped weapons don't clip wall colliders).

**main.ts wiring**: `const arena = createArena(world); world.arena = arena;` — happens BEFORE `createPlayer`. The player spawns deterministically at `arena.spawnPoints[0]` (S1, west side) — `createPlayer(world, spawn0.position)` is called explicitly with S1's coords, then `Rotation.y[playerEid] = spawn0.facing` is written manually because the explicit-position path leaves yaw at 0. The shopkeep moves to `arena.shopkeepStall.npcAnchor = (-12, 0.1, 13)` (was the v0 arbitrary `(8, _, 8)`) so the NPC actually stands behind the SW counter. `DUMMY_SPAWN_POSITIONS` is replaced by `getDummySpawnPositions(world)` which reads the four interior spawns S2/S3/S5/S6 (indices 1/2/4/5) from `world.arena.spawnPoints`, with a small inline fallback for tests that build a world without an arena.

**No shadows.** `castShadow` / `receiveShadow` / `renderer.shadowMap` are deliberately not enabled in v1 — they require shadow-camera tuning, biases, and a perf budget the low-poly aesthetic doesn't warrant. The lighting rig (ambient + hemisphere + sun directional, all from #117) is preserved verbatim by #112.

**Cleanup**: the v0 `src/ecs/entities/createArena.ts` (procedural box obstacles + GridHelper) is deleted — no consumers had imported it since `main.ts` switched to `./arena/createArena`.

See `docs/arena-v1.md` for the full layout / coordinate / lighting tables.

### Weapon Pickup Visuals (#127 — PR #165)

### Animation Foundation (#120 — PR #152)
Backend groundwork for the animation rebuild (#89, #110). Five pieces, all additive:

- **`CombatStateComp.phaseT: f32`** — synced each fixed tick from `fsm.getPhaseT()` alongside the existing `phaseElapsed`/`phaseTotal` (ui16). AnimationSystem reads `phaseT` to drive pose interpolation. Per the FSM v2 spec, this field will move onto the unified `CombatState` component when #88 lands.
- **`HitReactComp` + `HitReactSystem`** (`src/ecs/components.ts`, `src/ecs/systems/HitReactSystem.ts`) — `{dirX, dirY, dirZ: f32, magnitude: f32, spawnedAtTick: ui32, durationTicks: ui16, active: ui8}`. `DamageSystem.handleHit` populates it on every successful unblocked hit, rotating the world-space attacker→target delta into the target's body-local frame via `-yaw` around Y; magnitude is `damage / max-direction-damage` clamped to `[0, 1]`; duration is **12 ticks (~200ms)**. Successful blocks/parries do NOT touch the component (sentinel test in `HitReactSystem.test.ts`). `HitReactSystem` runs **after** `DamageSystem` in `main.ts` so a fresh stamp doesn't get cleared the same tick it's written.
- **`src/core/tickCounter.ts`** — module-level fixed-tick counter (`currentFixedTick`). `advanceFixedTick()` is called **once at the top of `fixedUpdate`** in `main.ts` before any system that stamps events. Read via `getCurrentFixedTick()`; reset via `resetFixedTick()` (test helper). NOT incremented from variable-rate update/render — must advance in lockstep with the fixed timestep so consumers can compare `currentTick` to a previously-stamped `spawnedAtTick + durationTicks` with tick-precise semantics.
- **Dummies have a CombatFSM** — `createTrainingDummy` (#114, replacing the legacy `createDummy`) registers a `CombatFSM` in `fsmRegistry` so `CombatSystem`'s existing all-entities loop ticks dummies and populates `phaseElapsed`/`phaseTotal`/`phaseT` for them just like the player. `toggleTrainingDummyBlock`, `cycleTrainingDummyBlockDirection`, and `resetAllTrainingDummies` all route through the FSM transition API (Idle → Block now goes through `ParryWindow` first, exactly like the player). New `CombatFSM.setBlockDirection()` setter lets the cycle helper update direction without re-entering ParryWindow.
- **Bonus — combo recovery now actually works**: a latent bug where `_isComboRecovery` was never set to `true` was papered over by the old `computePhaseTotal` heuristic (`ticksRemaining <= comboRecovery → comboRecovery`). Fixed via a new `_currentSwingIsCombo` flag set on `_enterWindup(dir, fromCombo=true)` (combo path only) and consumed at Release expiry → `_enterRecovery(this._currentSwingIsCombo)`. Weapon configs' `comboRecovery` values are now actually applied as designed.

### AnimationSystem Rebuild (#128 — PR #166)
Implements `docs/animation-architecture.md` §9 against the foundation laid by #120. Replaces the legacy "exponential settling" / velocity-magnitude / fixed-60-40-spine system with a layered procedural animator. Pure additive plus a `AnimationComp` field swap; **no new deps, no schema**.

- **Three new shared helpers** under `src/animation/` so the third-person system AND the future `ViewmodelAnimationSystem` rebuild (issue #D) can share them — no more independently-buggy copies of the same blend math in two files.
  - **`poseBlending.ts`** — `applyPoseLayer(bones, prevPose, currentPose, easedT, ownedBoneSet)` + `smoothstepEase(t)` + `CROSSFADE_DURATION_SEC` (~80ms). The slerp source is the **captured snapshot** quaternion, NOT `bone.quaternion` live — that's the §10.1 "exponential settling" fix. Bones outside `ownedBoneSet` are skipped, so multiple layers can call this in the same tick without writing each other's bones.
  - **`arcSwing.ts`** — `ARC_SWING_PARAMS` per `Direction` + `computeArcSwingPose(direction, t)` that linearly lerps Euler endpoints on `shoulder_R / forearm_R / hand_R` (and `spine` for Overhead/Left/Right horizontal slashes — Stab gets no spine since a thrust has no follow-through). Per-weapon scaling landed in #132 — see "Per-weapon arc-swing tuning + Viewmodel sync (#132)" below. `ARC_SWING_OWNED_BONES` is the public set used by `AnimationSystem` to route arm bones through the arc and the rest through the keyframe.
  - **`hitReact.ts`** — `applyHitReactLean(spine, chest, dirX, dirY, dirZ, magnitude, t)` directional stagger overlay. Piecewise-linear intensity peaks at `t = 0.3` and decays to 0 by `t = 1`; ~30° max tilt; **multiplied on top of `HITSTUN_POSE`** (`bone.quaternion.multiply(reactQuat)`) so layer composition stays clean. No-op on null bones / inactive comp / zero magnitude / out-of-window t (six guards, all unit-tested).

- **`AnimationSystem.ts` full rewrite** against §9:
  - Reads `MovementState.{speedFactor, grounded, crouching}` directly — replaces the velocity-magnitude `sqrt(vx² + vz²)` heuristic from §10.5 + the hardcoded `isCrouching = false // TODO` from §10.6.
  - **Defensive against missing `MovementState`** — `createTrainingDummy` doesn't add it, so the system uses `hasComponent(world.ecs, MovementState, eid)` and defaults absent entities to "stationary, grounded, not crouching" (the natural idle pose). The bitECS slot polarity matters: `grounded === 1` means on the ground, so a raw read on an entity without the component gives 0 = airborne, which would render dummies in mid-jump pose every frame. The defensive fallback ALSO covers the player's first-frame airborne state where `createPlayer.ts` initializes `grounded = 0` before `MovementSystem` ticks.
  - Per-entity quaternion snapshot in `prevPoseSnapshots: Map<eid, Record<boneName, Quaternion>>` (matches `meshRegistry` / `fsmRegistry` pattern). Captured on every state-or-direction transition by cloning every bone's quaternion (~17 bones); used as the slerp source for the next blend.
  - `effectiveT = smoothstepEase(max(phaseT, crossfadeT))` covers both fixed-duration states and no-duration states (Idle/Blocking) per §6.
  - **Layer ownership computed per tick** — each bone owned by exactly one layer. Three layers: Movement (`thigh_L/R`, `shin_L/R`, `foot_L/R`), Combat (upper-body except spine), Idle arm-swing (overrides `shoulder_L/R` when `state === Idle && speedFactor > IDLE_SPEED_FACTOR_THRESHOLD`). Spine precedence: combat first iff combat pose has a spine entry, else movement iff its base pose does, else rest. Replaces the legacy `60% combat / 40% movement` spine blend that drifted as the layers changed.
  - **Release runs `computeArcSwingPose` for `shoulder_R / forearm_R / hand_R` with `smoothstepEase(crossfadeT)` blend** (NOT `max(phaseT, crossfadeT)`) — since the target moves with `phaseT`, double-blending would visually drag. Non-arm combat bones during Release follow the keyframe pose under the standard `effectiveT`.
  - HitStun overlays `applyHitReactLean` only when `HitReactComp.active === 1 && magnitude > 0`; the lean t is `(currentFixedTick - spawnedAtTick) / durationTicks`, clamped to `[0, 1]`. Read-only against `CombatStateComp` / `HitReactComp` / `MovementState` — the system writes only bone quaternions and `AnimationComp` fields.
  - **Spec note: combat layer is always active in the arm sense.** §5 says "Combat (upper-body keyframe + arc) — Active when `combatState !== Idle`", but `getCombatPose(Idle)` returns `IDLE_POSE` (the ready-stance sword guard) — without it, Idle would default arms to T-pose. The §5 wording governs spine ownership only; `computeOwnership` claims spine for combat iff the combat pose has a spine entry (`IDLE_POSE` does, `spine: { x: 2 * DEG }`).

- **`AnimationComp` collapsed `upperBlend` + `lowerBlend` → single `crossfadeT: f32`** — one timer drives the whole-character crossfade now that ownership is per-bone. Snapshot lives in the side-table because bitECS only stores numeric fields.
- **`AnimationData.ts`** added `UPPER_BODY_BONES_EXCEPT_SPINE` export. `SHARED_BONES` flagged `@deprecated` (kept exported for backward-compat; the fixed-ratio blend it backed is gone).
- **`prevPoseSnapshots`** added to Module-Level Singletons — same multi-world caveat as the rest of the registries; will move to `GameWorld` if multi-world ever lands.

- **`DamageSystem` attribution + DamageDealt event** — every successful (unblocked, unparried) hit now records `{attackerEid, weaponId, bodyRegion, tick}` into a per-victim attribution map and emits a `DamageDealt` payload (lethal or not). `getDamageAttribution(victim, currentTick)` returns null past the **300-tick (5 s)** window — that's how `processDeaths` decides whether to credit a killer or use `killerEid = 0` (suicide / environmental).
- **`processDeaths(died, world)`** (`src/ecs/systems/processDeaths.ts`) runs immediately after `healthSystemTick`. For each entity in `died` that's tagged `Player` OR `Bot` (dummies opt out — they regen via `tickDummyHealthReset`), it: (1) resolves the killer via `getDamageAttribution`, (2) emits a `DeathEvent`, (3) increments `Score.deaths[victim]` and (if attributed and not self-kill) `Score.kills[killer]`, (4) resets `Score.goldThisLife[victim] = 0`, (5) calls `fsm.reset()` and forces both `CombatStateComponent` + `CombatStateComp` to Idle, (6) zeroes `Velocity`, (7) calls a no-op `dropEquippedWeapon(victim, world)` stub from `InventorySystem`. **CRITICAL: dummies are excluded by the `Player|Bot` gate** — without it a dummy's HP=0 would emit a DeathEvent and double-count via `tickDummyHealthReset`.
- **CombatSystem + MovementSystem early-outs** — both systems now start their per-entity loop with `if (hasComponent(DeadTag, eid)) continue;` so dead entities don't read input, don't tick the FSM, and don't move. This pairs with `processDeaths`'s FSM reset to ensure dead players freeze cleanly mid-windup.
- **createPlayer default starter weapon: `'Longsword'`** (was `'Dagger'`) per the design doc decision. `main.ts` `initInventory(eid, ['Longsword'], 'Longsword', 'Longsword')` matches; the viewmodel `initialWeapon` is also Longsword. Dagger is now the cheapest weapon in the shop, not the starter.
- **`dropEquippedWeapon(eid, world)` stub** in `src/ecs/systems/InventorySystem.ts` — wired through `processDeaths` so the death pipeline is complete on its own timeline. The actual implementation (spawn `WeaponPickup` at feet, skip protected `starterWeapon`) is owned by #94 / #A2.
- **main.ts `fixedUpdate` ordering**: `inputSystem → combatSystem → movementSystem → staminaSystemTick → const {died, respawned} = healthSystemTick → processDeaths(died, world) → physics.step → hitboxSystem → dummyDamageObserver → TracerSystem → DamageSystem → hitReactSystemTick → tickDummyHealthReset → interactionSystem → EventBus.flush()`. EventBus.flush is the LAST thing each tick.
- **Resolved** (issue B / #134): position/HP/stamina reset on respawn + spawn-point selection + RespawnEvent emission. **Resolved** (issue C / #137 — PR #168): DeathScreen, Killfeed, Scoreboard HUDs now subscribe to the EventBus + read `DeadTag`/`RespawnPending`/`Score` — see "Death/Respawn HUD" section below. **Out of scope** (deferred to #94 / #A2): real `dropEquippedWeapon` body. **Out of scope** (FSM v2 / #88): unifying `CombatStateComponent` + `CombatStateComp` into a single `CombatState` component — `processDeaths` writes both today.

### Spawn-Point Registry + Respawn Flow (#134 — PR #159, second half of #93)
Closes the spawn/death/respawn loop end-to-end. Death side landed in #130; this slice picks where you respawn and actually puts you back on the map. Six pieces:
- **`src/world/SpawnPoints.ts`** — `SpawnPoint { id, position: {x,y,z}, yaw }` interface (feet-position + facing-radians, matches the feet-origin convention from #104) + module-level `spawnPointRegistry: Map<id, SpawnPoint>` + `registerSpawnPoint` / `clearSpawnPoints` helpers + `selectSpawnPoint({ enemies, minEnemyDistance?, random? }): SpawnPoint | null`. The selector is the design doc's 4-step weighted-away-from-enemies algorithm: empty registry → null; no enemies → uniform random; otherwise filter to candidates with distance-to-nearest-enemy ≥ `minEnemyDistance` (default **8.0**) and uniform-random over the safe set; if no candidate is safe, **max-min fallback** picks the candidate furthest from its nearest enemy (so a packed arena still respawns the player). `random` is the deterministic-test seam; defaults to `Math.random`. Distance is 3D Euclidean — Y matters. `seedPlaceholderSpawnPoints()` registers four corners at `(±10, SPAWN_HEIGHT, ±10)` with `yaw = atan2(-x, -z)` (facing origin) — **kept around for unit tests that don't spin up an arena, but no longer wired in production** since #112 / PR #164 made `createArena` register the real 6-point arena spawn list. **1-based ids so `id=0` stays the "no spawn point" sentinel** for `RespawnEvent.spawnPointId`.
- **`src/ecs/systems/processRespawns.ts`** — runs in `fixedUpdate` immediately after `processDeaths(died, world)`. For each eid in `respawned`: builds the live-combatant snapshot **once per tick** (two queries `[Position, Player]` + `[Position, Bot]` deduped via Set since bitECS queries are conjunctive — no built-in OR), filters out self defensively, calls `selectSpawnPoint({ enemies })`. On null → `console.warn` + skip (entity stays `DeadTag`'d on the floor; empty registry is treated as a config error, not runtime concern). On hit: writes `Position` + **`PreviousPosition`** + `Rotation.y`, drives the Rapier kinematic body via `setNextKinematicTranslation`, restores `Health.current = Health.max` and `Stamina.current = Stamina.max`, calls `resetEntityStaminaTracking(eid)`, calls `equipDefaultStarter(eid)`, removes `DeadTag` + `RespawnPending`, emits `RespawnEvent { eid, spawnPointId, tick }`. **CRITICAL: `PreviousPosition` write** prevents the render-tick `lerp(PreviousPosition, Position, alpha)` from tweening the model from death-location to spawn-point over one frame — without it you see a visible glide artifact at high framerates.
- **`getPhysicsBody(eid)` accessor on `MovementSystem`** — exposes the existing `bodyByEid` Map. Documented choice over `world.physicsWorld.getRigidBody(PhysicsBody.bodyHandle[eid])`: Rapier handles are composite floats that get truncated by the bitECS `ui32` `bodyHandle` slot, so the handle round-trip is **lossy**. Future systems that need to teleport / impulse an entity should use this accessor; `bodyHandle` stays as an audit value only.
- **`equipDefaultStarter(eid)` + `DEFAULT_STARTER_WEAPON = 'Longsword'`** on `InventorySystem` — single source of truth for "what does a freshly-spawned combatant equip". Both `createPlayer` (initial spawn) and `processRespawns` (every subsequent life) consult it so the two paths can't drift. Adds the starter to inventory if missing — covers the future world after #94 / #A2 lands `dropEquippedWeapon` and clears the prior life's weapon. Returns false if the entity has no inventory or `equipWeapon` rejects (FSM not Idle — shouldn't happen on respawn since `processDeaths` resets the FSM).
- **`resetEntityStaminaTracking(eid)` on `StaminaSystem`** — drops the per-entity regen-delay counter for one eid (vs. `resetStaminaTracking()` which clears every entity for test isolation). Without this the regen-delay window from the previous life carries over and the first post-spawn tick either regens immediately or sits idle for a full second. Per-entity, safe to call in production, no-op when the eid has no entry.
- **`createPlayer` initial-spawn registry path** — when the caller doesn't pass `spawnPos`, `createPlayer` consults `selectSpawnPoint({ enemies: [] })` (no live combatants exist yet at world-load time) and uses the chosen point's position + yaw. Falls back to `(0, raycast, 0)` if the registry is empty (unit tests that don't seed spawn points). Tests pass explicit `spawnPos` to keep deterministic positioning. **Update post-#112 / PR #164**: `main.ts` now passes `arena.spawnPoints[0].position` explicitly so the dev-path initial spawn pins to S1 deterministically (was non-deterministic-by-design under the placeholder regime); the registry-driven random-pick path still exists and is exercised by tests + by `processRespawns` for every subsequent life.
- **main.ts wiring** (post-#112 / PR #164): `createArena(world)` registers the 6 arena spawn points and is called BEFORE `createPlayer(world, arena.spawnPoints[0].position)` — `seedPlaceholderSpawnPoints()` is no longer wired in production. `processRespawns(respawned, world)` runs in `fixedUpdate` immediately after `processDeaths(died, world)`. Updated `fixedUpdate` ordering: `inputSystem → combatSystem → movementSystem → staminaSystemTick → const {died, respawned} = healthSystemTick → processDeaths(died, world) → processRespawns(respawned, world) → physics.step → hitboxSystem → dummyDamageObserver → TracerSystem → DamageSystem → hitReactSystemTick → tickDummyHealthReset → interactionSystem → EventBus.flush()`.
- **`Lifecycle.test.ts`** integration test — drives the real `healthSystemTick → processDeaths → processRespawns → EventBus.flush` chain. Pins `RESPAWN_DELAY_TICKS = 180` exactly (off-by-one regression check — counter starts at 180, decrements 179 times to 1, the final tick takes it to 0 and surfaces in `respawned`). Verifies `Score.deaths` persists across respawn, `Score.goldThisLife` stays 0 through respawn, second damage post-respawn doesn't immediately re-kill, non-fatal damage emits no `DeathEvent`.
- **Resolved**: HUD subscribers (`DeathScreen` / `Killfeed` / `Scoreboard`) — landed as issue C / #137 in PR #168 (see "Death/Respawn HUD" section below); real arena geometry — landed in #112 / PR #164 (the placeholder seam paid off mechanically with no `processRespawns` / `selectSpawnPoint` changes needed). **Out of scope**: real `dropEquippedWeapon` body (#94 / #A2 — still a no-op stub from #130).

### Gold Economy — `Gold` ECS Component + Kill-Attribution Pipeline (#103 — PR #146)
Foundation for the gold-currency feature (parent #95). Adds the `Gold` ECS component, wires gold-on-kill onto the existing `DeathEvent` pipeline from #130/#134, and introduces `goldEconomy.ts` as the single chokepoint for all gold mutations. Persistence (#105) and HUD migration (#108) build on top. Pure additive (716+/0− across 7 files); 26 new tests; no schema files; no new deps.
- **`Gold` ECS component** (`src/ecs/components.ts`) — `defineComponent({ amount: ui32 })`. Numeric-only per the bitECS constraint. Attached to the player on spawn in `createPlayer`. **`ui32` overflow** wraps at ~4.29B — practically unreachable via 25-per-kill gameplay (~171M kills) but if any future heuristic awards lump sums (admin/event drops), enforce a server-side cap. Persistence (#105) will overwrite `Gold.amount[eid]` after reading from `localStorage`.
- **`src/economy/goldEconomy.ts`** — the chokepoint module. `GOLD_PER_KILL = 25` (frozen by spec — exported so #105 tests don't hard-code). `awardGold(playerEid, amount, reason)` returns the new balance; **no-op for non-positive amounts** (returns current balance unchanged, does NOT fire listeners) so future heuristics that compute their own amounts can opt into a clean "no reward" outcome without conditionals at the call site. `awardGoldOnKill(world, victimEid, attackerEid)` enforces the 4 attribution rules from `docs/gold-currency.md` §2 in order: (1) env death (`attackerEid === undefined`) → null; (2) self-kill (`attackerEid === victimEid`) → null; (3) non-`Player` attacker → null; (4) defensive — attacker missing `Gold` component → null. Returns the attacker's new balance or null. The 5th "already-dead" guard lives upstream in `DamageSystem`'s `attributionByVictim` map → `processDeaths` chain (5 s / 300-tick `ATTRIBUTION_WINDOW_TICKS`); posthumous damage past the window resolves to `killerEid = 0` and is mapped to `attackerEid === undefined` at the EventBus subscription. `onGoldAwarded(fn)` / `offGoldAwarded(fn)` pubsub for HUD (#108) and persistence (#105) — listeners fire AFTER the balance is updated. `AwardReason = 'kill' | 'admin'` is a metadata label on the event payload, NOT an authorization grant; admin commands must gate at the call site (e.g. `import.meta.env.DEV` and/or server allowlist), never via the reason string.
- **Wiring via `DeathEvent` (the architecturally important call)**: `main.ts` subscribes `EventBus.on('DeathEvent', ({victimEid, killerEid}) => awardGoldOnKill(world.ecs, victimEid, killerEid === 0 ? undefined : killerEid))`. The death-pipeline data — attacker resolution, weapon ID, body region, the 5 s attribution window — already lives in `DamageSystem.attributionByVictim` + `processDeaths` from #130/#134. Gold-on-kill is a pure consumer; **no parallel attribution path in HealthSystem**. The `killerEid === 0 → undefined` mapping bridges the EventBus's "0 = sentinel" convention to `awardGoldOnKill`'s `undefined` env-death rule. This is the same shape the future server-authoritative path takes — when networking lands, server-emitted `DeathEvent` payloads fan out to the same handler.
- **`Wallet.ts` ↔ `Gold` ECS bridge (transitional)**: `src/economy/Wallet.ts` is the **current** source of truth for the player's gold balance — `GoldCounter` HUD subscribes to `onGoldChange`, `ShopPanel` displays `Wallet.getGold()`, `PurchaseFlow` spends via `Wallet.spendGold`. The `Gold` ECS component is the migration target per `docs/networking/04-server-packaging.md §3`. To keep the HUD/shop in sync with kill rewards during the migration window:
  1. `createPlayer` initializes `Gold.amount[eid] = getGold()` (NOT `0`) so the ECS slot starts in sync with the Wallet default (200).
  2. `awardGold` **double-writes** — `Gold.amount[eid] = newBalance` AND `Wallet.addGold(amount)`. The Wallet write fires `onGoldChange` so the HUD updates immediately.
  3. The bridge is **one-way for now**: awards reach Wallet, but `Wallet.spendGold` (PurchaseFlow) does NOT write back to `Gold.amount[eid]`. Drift between the two is expected and deliberate for this PR's scope — fixing it requires migrating the HUD/shop READS to the ECS slot, which lives in #105/#108.
  4. Once #105 (persistence) and #108 (HUD) finish migrating their reads to `Gold.amount[eid]`, both the `walletAddGold(amount)` line in `awardGold` AND `Wallet.ts` itself become deletable.
- **Loop ordering — UNCHANGED**: the existing `fixedUpdate` order (`...DamageSystem → healthSystemTick → processDeaths → processRespawns → ... → EventBus.flush`) already runs `DamageSystem` BEFORE death detection (records attribution per-hit), and `processDeaths` resolves the killer from attribution + emits `DeathEvent` BEFORE `EventBus.flush()` drains the queue. The PR added an `EventBus.on('DeathEvent', ...)` subscription block in `main.ts` (next to the existing `RespawnEvent` viewmodel-snap subscription) — no `fixedUpdate` ordering changes required.
- **Module-Level Singletons** addition: `goldEconomy.listeners` array is per-process — same multi-world caveat as `EventBus.handlers`, will move to `GameWorld` once a server runs multiple worlds in one process.
- **300-tick attribution window invariant**: `ATTRIBUTION_WINDOW_TICKS = 300` (5 s) is now load-bearing for kill-credit. Currently `300 > RESPAWN_DELAY_TICKS = 180` so a respawning victim's previous-life attribution is still resolvable. **If `RESPAWN_DELAY_TICKS` ever grows past 300, `ATTRIBUTION_WINDOW_TICKS` MUST grow with it** — otherwise late-tick kills emitted at the boundary lose attribution and silently award 0 gold.
- **Out of scope**: persistence (`localStorage` + load-time validation — **resolved by #105 / PR #170**, see "Gold Persistence" below); HUD migration of `GoldCounter` to read `Gold.amount[eid]` instead of `Wallet.getGold()` (#108); earning gold from time / round bonuses (#95); per-bot wallets (post-#92, when bots become networked players). **Forward-looking security** (carry-forward from PR #146 review): when persistence lands, treat client-side `Gold.amount` as a display cache; server (or, pre-server, the localStorage writer) owns gold authority. Tampered values must be `Number.isInteger` + range-checked + clamped to `[0, MAX_GOLD]` before assignment.

### Gold Persistence — Player Identity + localStorage Save/Load (#105 — PR #170)
Persistence layer for the gold currency design (`docs/gold-currency.md` §3, §6, §10). Pure additive (1031+/0− across 8 files; 49 new tests; 1338/1338 green post-merge). No new deps, no schema changes. Two new modules + wiring at three seams (`createPlayer`, `awardGold`, `beforeunload`).
- **`src/economy/playerIdentity.ts`** — browser-scoped stable id. `getOrCreatePlayerId()` reads `bb_player_id` from localStorage on first call; if absent, generates a fresh `crypto.randomUUID()` and writes it back. Cached in-process so subsequent calls are reads from a module-level scalar (`cachedPlayerId`). `attachPlayerIdentity(eid)` registers it in `playerIdentityRegistry: Map<eid, string>` (matches `meshRegistry`/`fsmRegistry`/`inventoryRegistry` side-table pattern — bitECS components are TypedArray-backed and can't hold strings). `getPlayerId(eid)` returns `undefined` for entities without an identity (dummies, NPCs, bots, test paths). Defensive `Math.random` UUID fallback for environments where `crypto.randomUUID` is unavailable; single-warning gates (`warnedAboutStorage`, `warnedAboutRandomUUID`) prevent console spam in private-browsing / quota-exceeded paths. `clearPlayerIdentityRegistry()` is the test helper — clears both the registry AND the cached id AND the warning gates.
- **`src/economy/goldPersistence.ts`** — `bb_gold_<playerId>` keyed save/load. `loadGold(id)` is synchronous, validates: missing key → 0; `Number.isFinite + Number.isInteger + non-negative` → parsed value clamped at `Number.MAX_SAFE_INTEGER`; **anything else → 0 with a SINGLE warning per invalid key** (so reloading a tampered value doesn't spam — a `warnedInvalidValues: Set<string>` tracks per-key gates). `saveGold(id, n)` is **trailing-edge debounced 100 ms** — rapid kill sequences coalesce into a single `setItem` per quiet window (the integration test pins this with an 8-kill flurry → 1 `setItem`). Pending writes live in `pendingWrites: Map<string, number>` keyed by playerId; the latest amount wins. Negative amounts clamp to 0 before storage; non-finite (NaN/Infinity) are dropped without scheduling a write. **`flushGoldWrites()` is the synchronous escape hatch** — called by `main.ts` `beforeunload` so the last in-flight award isn't lost on tab close, and by tests that want to assert without awaiting a real timer. Failing flushes **snapshot-then-clear** the pending map FIRST, so a transient quota error doesn't leave the map growing forever — the player's session continues on the in-memory `Gold.amount`. Single-warning gate `warnedSaveFailure` covers all storage-write failures in a session.
- **`hasPersistedGold(id)`** — the contract that lets `createPlayer` distinguish "first-launch — keep the Wallet default (200)" from "explicit-0 balance — overwrite to 0". `loadGold` collapses both to 0, so without this helper a returning player who'd spent down to 0 would be re-granted the 200-default on every session. Returns `false` if `localStorage` is unavailable / throws — callers treat that as no-entry and leave the in-memory balance untouched (a warning will fire from the eventual `loadGold` call if it's needed).
- **Wiring (3 seams)**:
  1. `createPlayer.ts` — AFTER `Gold.amount[eid] = getGold()` (the Wallet bridge default from #103), call `attachPlayerIdentity(eid)` and IF `hasPersistedGold(playerId)` then overwrite `Gold.amount[eid] = loadGold(playerId)`. Order matters — the Gold component must already exist before the overwrite.
  2. `goldEconomy.ts` `awardGold()` — AFTER the balance write (`Gold.amount[playerEid] = newBalance`) AND the Wallet double-write, look up `getPlayerId(eid)` and call `saveGold(id, newBalance)` if present. Bots / unattached entities are silently skipped (the persistence layer is per-player-id, not per-entity).
  3. `main.ts` — `window.addEventListener('beforeunload', () => flushGoldWrites())` near loop teardown. Synchronous, never throws (the catch-and-warn-once is inside `flushGoldWrites`), does NOT call `event.preventDefault()` so it can't block the unload. MDN-recommended over the deprecated `unload` (which is unreliable on mobile).
- **localStorage-access constraint** (per #105 issue): the ONLY two modules in the codebase that import `localStorage` are `playerIdentity.ts` and `goldPersistence.ts`. `createPlayer` consults `hasPersistedGold` rather than reaching into storage directly. Tests that need to seed/inspect storage do so directly via `localStorage.setItem` + the exported `goldStorageKey(playerId)` helper. **When adding any new persisted state (settings, keybinds via #87, etc.), put the localStorage access in a new dedicated module under the relevant feature directory — do NOT add `localStorage` imports to gameplay code.**
- **Multi-tab is intentional MVP behavior — last-tab-wins.** No `storage` event subscription. Two tabs awarding gold in parallel will overwrite each other's writes; the last `setItem` to fire wins. Acceptable because (a) MVP is single-player, (b) multi-tab is an edge case, (c) the real long-term answer is server-authoritative balance post-#92 networking.
- **Forward-looking security** (carry-forward from PR #146): the validation in `loadGold` is what closes that promise — `Number.isInteger` + non-negative + clamped at `MAX_SAFE_INTEGER` before assignment. Tampered storage values cap out at the integer bound and surface a single warning. Once #92 networking lands, the server becomes the gold authority and `loadGold` becomes a display cache only — but until then, this module is the source of truth.
- **Module-Level Singletons** addition: `playerIdentityRegistry` (Map<eid, string>), `cachedPlayerId` (string|null), warning gates, `pendingWrites` (Map<string, number>), `pendingTimer` (handle|null), `warnedInvalidValues` (Set<string>) — all per-process. Same multi-world caveat as the rest; will move to `GameWorld` once a server runs multiple worlds in one process. Tests reset via `clearPlayerIdentityRegistry()` + `resetGoldPersistence()`.
- **Out of scope**: HUD migration of `GoldCounter` to read `Gold.amount[eid]` instead of `Wallet.getGold()` (#108); README updates (#108 owns); earning gold from time / round bonuses (#95); server-authoritative balance (Phase 2 after #92).

### 2026-07 Combat Overhaul — the "game is unplayable" root-cause pass
A goal-directed sweep (2026-07-05) found and fixed five compounding runtime bugs that made combat non-functional despite 1,565 green unit tests (every test mocked Rapier and/or the scene graph). The new `src/__tests__/CombatEndToEnd.test.ts` boots REAL Rapier + real entity factories + the full fixedUpdate loop and is the regression gate for all of them. Verified end-to-end in a headless browser (playwright-core + system Chrome, synthetic `mousemove` events for pointer-locked aim — CDP mouse events carry no `movementX`).

1. **Arc-swing geometry was backwards** (`src/animation/arcSwing.ts`): Overhead chopped down the player's BACK and through the ground under their feet; Left/Right swept the player's own chest plane (z≈0, unreachable by any target in front); Stab thrust backwards. Rewritten against the actual bone math (`dir = Rx·Ry·Rz·(0,-1,0)`, forward −Z): chops sweep up-back → forward → thigh-height, slashes ride a horizontal front-hemisphere plane at `shoulder x=1.35` + z sweep, stab ease-outs to full extension by phaseT≈0.6 (linear ramps left long weapons pointing underground for the whole Release). Overhead/Stab get a small `z` convergence so the blade lands on the crosshair line instead of a shoulder-width right of it; convergence is deliberately SMALL for Stab (scales with reach — a spear over-corrects half a meter). Windup/release/block keyframes in `AnimationData.ts` re-authored to chamber INTO the arc starts (old chest twists and Left/Right chambers were sign-flipped).
2. **Player mesh never rotated with aim**: `Rotation.y` was written by MovementSystem but nothing copied it to the Three.js group — the weapon bone (tracer source) swept the same world arc regardless of look direction. `hitboxSystem` now syncs group position+yaw from ECS before physics queries (fixed-rate, covers TracerSystem), and main.ts's render loop lerps `PreviousRotation→Rotation` for smooth visuals.
3. **Directional input collapsed to Stab**: `detectDirection` compared a per-mousemove-event MEAN against a 12px threshold — detection depended on the mouse's report rate. Now uses `InputManager.getAccumulatedDelta` (total pixels over the 100 ms window) with `stabThreshold: 30`.
4. **Dummy damage healed instantly** (the literal "damage doesn't work"): `NpcDamageObserver` polled `DamageEvent` ECS entities but ran BEFORE TracerSystem created them and DamageSystem deleted them the same tick → `recordNpcHit` never fired → `tickTrainingDummyHealthReset` saw "unhit for 3 s" on every tick and restored full HP. Observer is now EventBus-driven (`DamageDealt` subscription — ordering-immune; its per-tick fn is a no-op kept for call-site shape) AND the regen check moved BEFORE hit detection in fixedUpdate (a post-DamageSystem check heals fresh wounds the same tick because `recordNpcHit` lands at flush time).
5. **First-person weapon invisible** (the un-filed post-#181 mystery): FP idle poses hung the arm at ~65° total chain rotation — the hand sat 0.69 m below the camera, UNDER the fov-70 frustum's bottom plane, with the blade pointing further down. Idle chains raised to ~98° (hand lower-right in frame) and every weapon's `gripRotation.x` sign flipped (blades now point up-forward, ready-stance). `ARM_OFFSET.x` 0.32→0.42 frames the weapon right-of-center.

**New systems/content in the same pass:**
- **Physics knockback** (`KnockbackState` component + `src/ecs/systems/KnockbackSystem.ts`): per-weapon `WeaponConfig.knockback {force, upward}` applied by DamageSystem on unblocked hits along attacker→target. Players integrate it through MovementSystem's character controller (input suppressed while `ticksRemaining > 0` — no steering mid-tumble, no jump); non-player entities (dummies) get ballistic integration + fixed-body teleport with ground friction, air drag, bounce restitution 0.35, and an arena-bounds clamp. Beware the f32/f64 epsilon: `Position` reads back `0.1` as ~0.100000001, so ground contact uses `GROUND_EPSILON = 1e-3` (a strict `<= GROUND_TOP_Y` check leaves victims sliding frictionlessly forever). Verified live: warhammer overhead launches a dummy 5 m with visible arc + bounce.
- **Six new weapons** (10 total): Zweihander (reach), Warhammer (max launch), Spear (2.4 m stab specialist), Katana (combo tempo), Scythe (blade rides a ~2 m ring — INSIDE the ring is the safe zone, `range: 2.4`), Yeeter (a tree trunk; damage 12-25, knockback 16/10 — pure launch toy, 500 g). Registration surfaces per weapon: config file (auto-registers on import in main.ts + the E2E test), `weaponIdToName` (APPEND ONLY — ids are wire format), `weaponModelFactories`, `PICKUP_ORIENTATIONS` (default exists), `Prices.ts`, `WEAPON_SCALING` + `WeaponName` in arcSwing.ts. FP poses and arc params fall back to Longsword for unregistered names.
- **Movement tuning** (`core/types.ts`): WALK 4.5, SPRINT 7.5, GRAVITY −22, JUMP_VELOCITY 9 (apex ≈1.84 m, ≈0.82 s air) — bouncy arcade hops; jump is edge-triggered with no cooldown (bunny-hopping is intended).
- **Automation seams in main.ts**: `window.__getPlayerState()` / `window.__getNpcs()` read-only ECS snapshots (position/yaw/hp/combat state/knockback) consumed by the headless-browser verification driver; `setWeapon(name)` dev helper now self-provisions inventory.
- **`getAverageDelta` is deprecated** in favor of `getAccumulatedDelta`; remove once nothing imports it.

### 2026-07 Fluidity Pass — "stuck after swinging" root causes
Follow-up to the combat overhaul (same goal session). Four independent things locked the player after every swing; all verified fixed live in the headless-browser harness (chained hits ~800 ms apart while mashing; measurable turn during Release; uncapped aim in Recovery).

1. **Turncap unit bug — the big one** (`CameraController.processInput`): `maxTurnRate` is radians per FIXED TICK (the `WeaponConfig.turncap` unit) but the clamp multiplied by another 1/60 as if converting rad/s → rad/tick. Every cap was 60× harsher than authored — windup's "275°/s" was really ~4.6°/s; the mouse effectively froze during every swing phase. Now scales one tick's budget by measured frame dt (`maxTurnRate · dt · 60`) so 144 Hz frames can't out-turn 60 Hz ones. If a turncap ever "feels dead" again, check the units FIRST.
2. **Combo clicks sat out the full recovery**: buffering during Recovery set `_isComboRecovery` but the CURRENT `_phaseTotal` was already the full `recovery[dir]` — `comboRecovery` only applied to the recovery after the NEXT swing. `_handleAttack` now clamps the running recovery down to `comboRecovery` at buffer time. Also new: clicks during **Release** buffer (Mordhau-style input queueing — previously eaten), and Attack fires straight out of **Blocking** (no release-RMB-then-click dance). Contract tests: `src/combat/CombatFSMFluidity.test.ts`.
3. **Durations rebalanced across all 10 weapons**: recoveries cut ~40%, comboRecovery down to snappy chain gaps (longsword 8t, dagger 4–6t, yeeter still 13–18t), `hitStunTicks` cut to 22–38, `turncap.windup` loosened per class, `turncap.recovery = Infinity` for every weapon (post-swing aim is free; Release keeps the per-weapon drag cap — that's the skill mechanic), `turncap.hitStun` 0.005 → 0.02 (dazed, not frozen). Pinned by the every-weapon sweep in `CombatFSMFluidity.test.ts`.
4. **Knockback control-lock lingered after the tumble ended**: MovementSystem now returns control the moment the victim is grounded with knockback speed < 1 m/s (the timer is only an upper bound, trimmed to `min(60, speed·5)`), so being launched stays uncontrollable but lying still doesn't eat input.

Also: **stamina regen 5/s → 20/s, delay 60 → 45 ticks** (an empty bar took 20 s to refill; fights parked while the meter crawled).

**Browser-driver gotcha** (cost an hour): `page.mouse.down(); page.mouse.up()` back-to-back completes within one 16 ms fixed tick — CombatSystem's edge detector samples button state once per tick and never sees the click. Hold the button ≥ ~45 ms in automation.

Trust model (documented in `src/net/protocol.ts`): the server owns roster, scoreboard, HP, deaths/kill credit, respawns, and the **15-minute match clock** (intermission 10 s, scores reset, everyone respawns); movement is client-authoritative relay at 20 Hz; hits are ATTACKER-CLAIMED with server sanity caps (`server/room.ts`: per-claim ≤ 80 dmg, ≥ 250 ms per attacker→victim pair, ≤ 7 m range vs fresh reported positions, alive checks, match-live check). `claim` is exactly the message that disappears when doc-04's CoreWorld lands. JSON frames v1 (msgpackr is a doc-02 migration, not a semantic change).
- **Server** (`server/`): `room.ts` is pure/transport-free (fake-clock unit tests in `room.test.ts` — vitest include now covers `server/**`); `index.ts` = static dist + `/healthz` + WS + optional Supabase token verification (fetch to `auth/v1/user`; profile username wins; sanitized guest fallback). `npm run dev:server` (tsx, :3004; vite proxies `/ws`), `build:server` (esbuild bundle), Dockerfile now runs the Node server (replaced nginx; same single-port deploy contract).
