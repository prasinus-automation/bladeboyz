# Spawn / Death / Respawn Loop — Architecture

**Source issue**: [#93](https://github.com/prasinus-automation/bladeboyz/issues/93)
**Status**: Architect-approved design. Implementation tracked in sub-issues (see bottom).

This document defines the lifecycle of a player from join → spawn → fight → die → respawn → fight, and the events, components, and systems that drive it. It is the single source of truth for spawn/death/respawn behavior; sub-issue PRs must conform to it.

---

## Decisions

| Question (from #93) | Decision | Rationale |
|---|---|---|
| **Default starter weapon** | **Longsword** | Mid-tier reach/damage/speed. A bare-hands fallback adds a weapon config and FSM tuning we don't need yet. Once Gold/Shop (#95/#96) lands, players can buy their loadout; until then Longsword is the universal floor. |
| **Respawn timer** | **3.0 s (180 ticks @ 60 Hz)** | Per issue body recommendation. Tunable via `RESPAWN_DELAY_TICKS` constant; long enough to feel like a penalty, short enough to keep deathmatch flow. Existing scaffolding ships at 120 ticks — bump to 180. |
| **Spawn-point selection** | **Random pick, weighted away from enemies.** Filter candidates whose nearest enemy is within `MIN_ENEMY_DISTANCE = 8.0` units; if filter is empty, fall back to **max-min-distance** (the candidate furthest from the nearest enemy). Among survivors of the filter, uniform random. | Avoids spawn-camping without being deterministic. The fallback guarantees we always spawn somewhere, even on a tiny map. |
| **Score tracking** | **`Score` ECS component** (`kills: ui16, deaths: ui16, goldThisLife: ui32`). Persistent across deaths; `goldThisLife` resets on death (issue body wording). Total persistent gold lives in a separate component (out of scope, owned by #95). | ECS component (not side-table) so the future networking layer (#92) can serialize it per-entity with the rest of player state. |
| **Round model** | **Continuous deathmatch — no rounds for MVP.** | Confirms issue body recommendation. Rounds add scoreboard reset logic, lobby states, win conditions, match timer — none of which fit MVP scope. Scoreboard accumulates indefinitely until the player leaves. Revisit if/when game modes are designed. |
| **Killfeed entry** | Generated by a new `DeathEventBus` consumed by `Killfeed.ts`. Each `DeathEvent` carries `victimEid`, `killerEid` (or `0` for environmental/suicide), `weaponId`, `bodyRegion`. Killfeed maps eids → display names. | Death attribution must be capturable now even though display names will arrive with #92 networking; we can stub names as `"Player"` / `"Dummy"` in the meantime. |
| **Dead entities & the FSM** | On death: call `fsm.reset()` (already exists at `CombatFSM.ts:423`), force `CombatStateComp` to `Idle`, freeze movement (zero velocity, disable input read in `CombatSystem` for entities with `DeadTag`). | Prevents dead players continuing a swing or reading input during the 3 s timer. |
| **Drop equipped weapon on death** | **Yes**, gated on issue [#94](https://github.com/prasinus-automation/bladeboyz/issues/94) (Weapon drop & pickup). Until #94 lands, the death cleanup hook calls a stub `dropEquippedWeapon(victimEid)` that no-ops. | Keeps the death pipeline complete on its own timeline; #94 fills in the no-op. |
| **Dummies vs. Players** | Dummies opt OUT of the respawn flow. Their existing regen via `tickDummyHealthReset()` is preserved. Sub-issue A adds an `Ephemeral` (no-respawn) marker so HealthSystem only fires `DeathEvent` for entities tagged `Player` or `Bot`. | Dummies are training rigs. They never "die" in the killfeed sense and shouldn't fire respawn events. |

## Lifecycle State Diagram

The lifecycle is **not a CombatFSM state** — it's a higher-level entity state, expressed via two component tags (`DeadTag`, `RespawnPending`) plus `Health.current`.

## Event List

All events flow through a lightweight in-process bus (`src/events/EventBus.ts` — new module, sub-issue A). Consumers subscribe; the bus is drained at end of fixed-update tick. **No multiplayer concerns yet** — when #92 lands, server-authoritative events will be replicated as snapshots; the bus stays local.

| Event | Producer | Consumer(s) | Payload |
|---|---|---|---|
| `DamageDealt` | `DamageSystem` after applying HP delta | `Killfeed` (debug), `FloatingDamage` HUD | `{ victimEid, attackerEid, amount, bodyRegion, weaponId, isLethal }` |
| `DeathEvent` | `HealthSystem` when HP first crosses to 0 | `Killfeed`, `DeathScreen`, `Score` updater | `{ victimEid, killerEid, weaponId, bodyRegion, tick }` |
| `RespawnEvent` | `HealthSystem` when timer expires | `DeathScreen` (hide), `Spawn` debug log | `{ eid, spawnPointId, tick }` |
| `WeaponEquipped` | `InventorySystem` (already exists informally) | `Killfeed` (resolve weapon name) | `{ eid, weaponId, weaponName }` |

**`killerEid = 0`** is the sentinel for "no killer" (suicide/environmental). Eid 0 is never a valid bitECS entity, so this is unambiguous.

**Attribution rule**: the killer is the `attackerEid` of the most recent `DamageEvent` against the victim within a 5-second attribution window. If no recent damage exists (e.g., fall damage when that lands), `killerEid = 0`.

## Components Added

All new components live in `src/ecs/components.ts`.

/** Per-entity respawn countdown. ticksRemaining is decremented by HealthSystem. */

**Migration of existing `respawnTimers` Map** → `RespawnPending` component. The Map side-table in `HealthSystem.ts:44` is removed; `isDead(eid)` becomes `hasComponent(DeadTag, eid)`.

## Spawn-Point Registry (interface contract for #91)

```ts
// src/world/SpawnPoints.ts (new module)

export interface SpawnPoint {
  id: number;
  position: { x: number; y: number; z: number };
  yaw: number; // facing direction in radians
}

/** Side-table; populated by createArena() (#91 will redesign this). */
export const spawnPointRegistry = new Map<number, SpawnPoint>();

export function registerSpawnPoint(point: SpawnPoint): void;
export function clearSpawnPoints(): void;

export interface SpawnSelectionOptions {
  /** Entities to weigh away from (typically all live combatants). */
  enemies: number[];
  /** Minimum distance for "safe" spawn. Default 8.0. */
  minEnemyDistance?: number;
  /** RNG hook for deterministic tests. */
  random?: () => number;
}

/** Returns the chosen SpawnPoint, or null if registry is empty. */
export function selectSpawnPoint(
  options: SpawnSelectionOptions,
): SpawnPoint | null;
```

**Algorithm (`selectSpawnPoint`)**:

```
candidates = [...spawnPointRegistry.values()]
if candidates.length === 0: return null
if enemies.length === 0: return random pick from candidates

For each candidate, compute distToNearestEnemy.
safe = candidates.filter(c => c.distToNearestEnemy >= minEnemyDistance)
if safe.length > 0: return random pick from safe
else: return argmax(candidate.distToNearestEnemy)
```

Until #91 ships, sub-issue B seeds the registry with **4 placeholder spawn points** at `(±10, SPAWN_HEIGHT, ±10)` so the loop is testable end-to-end. When #91 lands, those placeholders are replaced with the real arena layout.

## System Integration Points

### `main.ts` fixedUpdate ordering (changed lines marked **NEW**)

```ts
combatSystem();         // skips DeadTag entities
movementSystem();       // skips DeadTag entities
staminaSystemTick();
const { died, respawned } = healthSystemTick(world.ecs);  // NEW: capture return
processDeaths(died, world);                                // NEW: cleanup hook
processRespawns(respawned, world);                         // NEW: spawn hook
world.physicsWorld.step();
hitboxSystem(world);
dummyDamageObserver();
TracerSystem(); DamageSystem();
tickDummyHealthReset();
EventBus.flush();                                          // NEW: drain events
```

### `CombatSystem` early-out

Add `hasComponent(DeadTag, eid)` early-skip at the top of the per-entity loop in `CombatSystem.ts`. Dead entities don't tick FSMs, don't read input, don't sync `CombatStateComp`.

### `MovementSystem` early-out

Same early-out for `DeadTag`. Velocity is zeroed at death (in `processDeaths`); without input, dead entities stay put.

### `InventorySystem`

Add `equipDefaultStarter(eid)` helper that wraps existing `equipWeapon(eid, 'Longsword')`. Called from `processRespawns`.

### `HealthSystem` refactor

- Remove `respawnTimers` Map; use `RespawnPending` component.
- `healthSystemTick` no longer manages position/stamina/FSM reset — that's done by `processRespawns` in `main.ts`.
- `healthSystemTick` returns `{ died, respawned }` arrays as today; `main.ts` now consumes them.
- `RESPAWN_DELAY_TICKS` becomes a **default**; `RespawnPending.ticksRemaining` is the per-entity source of truth (allows future per-mode overrides).

## HUD Surfaces

| Module | Behavior |
|---|---|
| `DeathScreen.ts` (new) | Full-screen dim overlay shown while local player has `DeadTag`. Top: "Killed by &lt;name&gt; with &lt;weapon&gt;". Center: large countdown number ticking 3 → 0. |
| `Killfeed.ts` (new) | Top-right stack of recent `DeathEvent`s. Each entry: `<killer> [<weapon-icon>] <victim>`. Entries fade after 5 s; max 5 visible. |
| `Scoreboard.ts` (new) | Persistent K/D display, top-left under HealthBar. Reads local player's `Score` component each frame. Tab-key full scoreboard is out of scope (deferred to #98). |

All three modules read from the local-player eid (`world.playerEntity`) and the `EventBus`.

## Testing Strategy

Each sub-issue ships with `*.test.ts` files matching the existing pattern (e.g., `HealthSystem.test.ts`, `selectSpawnPoint.test.ts`, `Score.test.ts`). Specifically required:

- `selectSpawnPoint` with no enemies → uniform random.
- `selectSpawnPoint` with enemies clustered near one point → that point is filtered out.
- `selectSpawnPoint` with all candidates within minDistance → returns the furthest one (max-min fallback).
- Death → DeadTag added, RespawnPending added with 180 ticks, fsm reset, velocity zeroed.
- Respawn → Health/Stamina restored, position teleported to a registered spawn point, default weapon equipped, DeadTag removed.
- DeathEvent emitted exactly once per death (not on subsequent damage to a dead entity).
- Score increments correctly on kill / death / suicide (killerEid=0).

## Sub-Issues

This design is implemented across three parallel-ish sub-issues:

- **A — backend-dev**: Death event pipeline + Score component + EventBus + `processDeaths` cleanup hook.
- **B — backend-dev**: Spawn-point registry + `selectSpawnPoint` + `processRespawns` (teleport, restore HP/stamina/weapon) + RespawnPending component + placeholder spawn points until #91 lands.
- **C — frontend-dev**: DeathScreen HUD + Killfeed HUD + Scoreboard HUD + README updates.

A and B are independent and can land in either order. C depends on the EventBus from A.

**External deps**: #94 (weapon drop) supplies the real `dropEquippedWeapon` body (stub for now). #91 (arena map) supplies the real spawn-point list (placeholders until then). #92 (networking) eventually replicates `DeathEvent`/`RespawnEvent` from server (out of scope here).
